# Automatic approval policy

Automatic approval is appropriate only for small, self-contained, low-risk changes
that a reviewer can read in one pass, such as a contained bug fix or refactor.

Require sufficient independent review of the current changes before approving.
Assess coverage and the substance of the reviews, rather than counting comments
or approvals. No particular review provider is mandatory. Explain why the existing
review coverage is sufficient; if it is missing, stale, partial, or inconclusive,
leave the PR for human review. Then perform your own independent review.

All discussions must be substantively addressed, including general PR comments
and resolved or outdated findings. Apply the relevant `AGENTS.md` instructions,
especially storage-format compatibility and sensitive information handling.

Require human approval for large changes, public API changes (including Swift,
Kotlin, and web exports), CI/workflow/release configuration, or any unresolved
correctness or security concern.

For dependency updates, inspect upstream release notes and source changes between
the old and new version. Verify the version and pinned commit or integrity hash.
Do not approve source/registry changes, new install/build hooks, unexpected
transitive dependencies, ownership changes, or updates whose provenance cannot
be established. Failure to obtain upstream evidence means human review.

Review requirements belong here in prose. For example, a repository could instead
require completed CodeRabbit and Copilot reviews covering the current changes,
with every finding addressed. That example is not a requirement for WalletKit.
